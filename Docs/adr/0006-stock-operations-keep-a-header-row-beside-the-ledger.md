# Stock operations keep a header row beside the ledger; returns only go trolley → warehouse; manual adjustments need evidence

The Transfer, Stock Return, Adjustment and Physical Count screens were create-only forms with no history (`.scratch/inventory-operation-history/spec.md`). Giving them history forced decisions the contract did not make; they are recorded here and `Docs/12` §13–14 was extended to match.

**Header rows beside the ledger.** A Transfer or Return writes a `stock_relocations` row and an Adjustment a `stock_adjustments` row, in the same transaction as its movements. The header's id is the value the movements already carried as `referenceId` (the adjustment's own movement id), so the ledger's loose reference now resolves to a row. The alternative — building history on the client by regrouping OUT/IN movement pairs from `GET /inventory/movements` — splits pairs across pages, cannot page by operation, and cannot show what an adjustment set the balance to: the ledger stores only the absolute variance. `stock_movements` itself is unchanged and stays the source of truth for balances (ADR-004); a header never moves stock. Existing operations were backfilled by the migration; manual adjustments made before it have no recoverable before/after quantities and keep them `null`, with reason code `OTHER`.

**A Stock Return is trolley → warehouse only.** Transfer and Return had become the same form, and users could not tell which to use. Return now requires a `TROLLEY` source and a `WAREHOUSE` destination; every other pair is a Transfer, which stays open to all four directions FR-WEB-012 lists.

**Adjustments carry a reason code, and a manual one needs evidence.** `Docs/02` §13's codes (`PHYSICAL_COUNT`, `DAMAGED`, `LOST`, `DATA_CORRECTION`, `OTHER`) replace the free-text-only reason, which becomes a note required for `OTHER`. Evidence is uploaded first (`POST /inventory/adjustments/evidence`) and claimed by the adjustment inside its balance transaction, keyed on uploader, factory and "not yet claimed", so a bad id or a lost race rolls the adjustment back. A two-step upload keeps the adjustment itself a JSON command under the shared idempotency middleware, rather than a multipart request. Adjustments written by completing a count session need no upload: the session and its counted items are the evidence. Orphaned uploads that are never claimed are not cleaned up yet.

**Count sessions can be cancelled.** `CANCELLED` is terminal and moves no stock, claimed with the same status compare-and-set as `complete` so the two cannot both win. Before this, abandoning a count only cleared the screen and left the session `OPEN` forever.

**History reads need `STOCK_VIEW`**, like the movement ledger, not the write permission of the operation listed.
