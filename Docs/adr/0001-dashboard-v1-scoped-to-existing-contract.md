# Dashboard v1 is scoped strictly to the existing `/dashboard/*` contract, built fixture-first

Docs 08 §9 and Docs 18 §10 describe a fuller Dashboard than `Docs/12-OpenAPI-Swagger-Specification.md` §15 actually contracts: the docs list 7 KPI items and 6 filter dimensions (Factory, Trolley, Date Range, Exchange Type, Needle Type, Operator), but the real `/dashboard/overview`, `/exchange-trend`, `/needle-consumption`, `/stock-summary` endpoints only support `factoryId`/`dateFrom`/`dateTo`(`/groupBy`), and `Backend/src/modules/reporting` doesn't exist yet (empty placeholder). Rather than build UI for filters and metrics the backend can't yet serve, Dashboard v1 (`WebApps/src/features/dashboard/`) ships only what the contract supports — 4 KPI cards (not 7), Factory + Period filters only (not 6) — and was built against local fixtures behind the real TanStack Query hook shape (`api/data-source.ts` is the single swap point) so implementation wasn't blocked on Backend.

**Consequences:** later WebApps modules should follow the same rule — implement against the documented contract, not the aspirational UI/UX spec, and flag the gap (this file) rather than build controls with nothing to back them. If Backend's `reporting` module ships richer filtering, revisit this decision rather than silently growing the UI past it.
