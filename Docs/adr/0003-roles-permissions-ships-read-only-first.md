# Roles & Permissions ships read-only first; role mutation is a separate ticket

Administration → Roles & Permissions has a data model (`Role`, `Permission`, `RolePermission`, seeded via `Backend/src/shared/constants/{roles,permissions}.ts`) and full enforcement (`RbacGuard`), but no runtime CRUD — grants are seed-only today, and `roles.ts`'s own comment notes "an admin can add more through the web app later," not yet built. `.scratch/client-authorization/spec.md` already flagged this module as the one with "no obvious code in the catalogue," using `USER_MANAGE` as a placeholder gate.

We decided to build a read-only screen first — list the five seeded roles, their permission grants, and which users hold each role — and defer role/permission mutation (create/edit a role, change its grants, assign a role to a user) to a later ticket. The read-only cut needs no new decision beyond what's already shipped (permission catalogue, role catalogue, `GET /users` from the Users read-API ticket); the mutation cut does not exist as a spec yet because it needs an answer this session did not resolve: **who is allowed to grant `USER_MANAGE`** (and, transitively, every other permission) **to whom**. Shipping mutation without that answer would let the first admin's ad-hoc, undocumented grant choices become the de facto policy before the real one is decided — the operational habit, once formed, is the expensive thing to undo, not the code.

**Consequences:** the "Roles & Permissions" nav entry launches read-only. `PATCH /users/:id/roles`, `POST /roles`, and `PATCH /roles/:id/permissions` stay unbuilt and undocumented-as-shipped (mirroring how `.scratch/users-read-api/spec.md` already left user-write endpoints out) until a follow-up spec resolves the grant-approval question. Until then, granting a role or permission remains a seed/database operation, same as it is today — this ADR does not change current operational reality, it only records why the UI doesn't paper over it yet.
