# Admin-panel writes never widen the caller's access, and a physical count never overwrites stock that moved after it was counted

Building the backend half of ADR-0004's tickets 01–06 forced a handful of decisions the contract (`Docs/12` §9, §13, §14, §16) did not make. They are recorded here, and `Docs/12` was extended to match.

**Users (ticket 06).** The admin sets a new account's first password (the user's choice over an emailed reset link; same rule as `ResetPasswordDto`), and create requires at least one factory scope — a user with no scope is outside every admin's scope and could never be listed, edited or granted anything again; for the same reason a user's last factory scope cannot be removed. Every grant follows the never-widen rule factory scope already had: a caller may only grant or remove factories inside their own scope, and only roles whose every permission they already hold. Without that, `USER_MANAGE` alone would be a path to any permission in the system — including the `ROLE_MANAGE`-level access ADR-0003 deliberately kept unresolved. Roles are addressed by code, the value `/users` and `/auth/me` already expose, not by id. A caller cannot deactivate their own account. User writes are audited as `CHANGE_CONFIGURATION`.

**Physical count (ticket 05).** A count session moves no stock until `complete`, which reconciles every non-zero variance through the same compare-and-set ADJUSTMENT write `POST /inventory/adjustments` makes, all in one transaction. Each counted item remembers the balance it was counted against; if that balance changed before `complete` — a receiving landed mid-count — nothing is written and the caller must recount, because setting the balance to a stale physical count would silently erase the receiving. Consistent with ADR-004 (backend as stock authority). No approval step: that policy is still ticket 08.

**Master data and inventory (tickets 01–04).** An inactive factory takes no new exchange, inventory write or count session (FR-WEB-017) — enforced where each transaction starts, not by cascading deactivation to trolleys, locations or devices. Creating a trolley creates its own `TROLLEY` location (ADR-003). Creating a factory grants its creator scope to it, or no one could see the new row. A stock return writes a pair of `RETURN` movements sharing one `returnId`, the same shape as a transfer.
